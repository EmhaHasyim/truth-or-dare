# Getting Started

This project uses [Bun](https://bun.sh) as its package manager (see `bun.lock`).

```bash
bun install
bun run dev
```

`bun run dev` automatically applies any pending D1 migrations and re-seeds the
local database (both are idempotent), so the local DB is always ready. The first
time new migrations exist, Wrangler asks for a one-time confirmation before
applying — subsequent runs are silent. Note that `dev` re-runs the seed on every
start (safe: it uses `INSERT OR IGNORE`).

# Building For Production

To build this application for production:

## Linting & Formatting

This project uses [Oxc](https://oxc.rs) tooling — `oxlint` (lint) and `oxfmt`
(formatter) — configured for the Solid + TanStack + Vitest + Workers stack.

| Command             | What it does                                                        |
| ------------------- | ------------------------------------------------------------------- |
| `bun run lint`      | Lint the codebase (`oxlint`) — correctness, suspicious & perf rules |
| `bun run lint:fix`  | Lint and auto-fix what's fixable (`oxlint --fix`)                   |
| `bun run fmt`       | Format the codebase (`oxfmt .`)                                     |
| `bun run fmt:check` | Verify formatting is clean (`oxfmt --check .`) — useful for CI      |

- Config lives in `.oxlintrc.json` and `.oxfmtrc.json` (both schema-linked).
- `oxlint` is deliberately tuned for this stack: the `vitest` plugin runs on
  test files only, React-centric `jsx-a11y` label rules are disabled (Solid
  uses `for`, not `htmlFor`), and rules that conflict with idiomatic Solid
  patterns (e.g. `ref={x}` assignment, `<Show>`-wrapped labels) are off.
- `oxfmt` matches the existing code style: single quotes, no semicolons,
  JSX double quotes, CRLF line endings, 100-char width. Generated files
  (`worker-configuration.d.ts`, `routeTree.gen.ts`) and `migrations/` are
  ignored.

> ⚠️ **If you edit the inline theme-restore script in `index.html`**, recompute
> its SHA-256 hash and update `script-src` in both `public/_headers` and
> `src/server.ts` (CSP blocks inline scripts without a matching hash).

## Database (D1 + Drizzle ORM)

The schema lives in `src/db/schema.ts`. Migrations are generated by
`drizzle-kit` into `migrations/<timestamp>_<name>/migration.sql` and are applied
by Wrangler's native, idempotent migration runner (tracked in the
`d1_migrations` table). `wrangler.jsonc` is configured with
`migrations_pattern: "migrations/*/migration.sql"` so Wrangler discovers the
Drizzle folder layout.

| Command                                                                         | What it does |
| ------------------------------------------------------------------------------- | ------------ |
| All `db:*` drizzle-kit commands (`db:generate`, `db:studio`) read Cloudflare    |
| credentials from `.dev.vars` — copy `.dev.vars.example` to `.dev.vars` and fill |
| in the `CLOUDFLARE_*` keys, otherwise drizzle-kit refuses to run.               |

| Command               | What it does                                                          |
| --------------------- | --------------------------------------------------------------------- |
| `bun run db:generate` | Generate a new migration from schema changes (`drizzle-kit generate`) |
| `bun run db:migrate`  | Apply pending migrations to the local DB (no-op when up to date)      |
| `bun run db:seed`     | Seed 500 truth questions (`INSERT OR IGNORE`, safe to re-run)         |
| `bun run db:reset`    | Full clean rebuild: drop all tables + migrate + seed                  |
| `bun run db:studio`   | Open Drizzle Studio (reads credentials from `.dev.vars`)              |

Typical workflow: after editing `src/db/schema.ts`, run `bun run db:generate`
then `bun run db:migrate` — or just `bun run dev`, which auto-applies
pending migrations. For a clean slate, run `bun run db:reset`.

> **Why not `drizzle-kit push`?** Drizzle-kit's `push`/`migrate`/`studio` talk to
> a **remote** D1 via Cloudflare's HTTP API (`accountId`/`databaseId`/`token`).
> They cannot reach the local Miniflare D1 inside `.wrangler/state/`. Applying
> migrations locally is Wrangler's job (`db:migrate`), and the same SQL files
> are reused for production via `wrangler d1 migrations apply --remote`. This
> is the officially recommended pattern for D1 + Drizzle.

> **Note:** local migrations live in `.wrangler/state/`. The scripts above are
> local-only. For the remote database, authenticate with `wrangler login` and run
> `wrangler d1 migrations apply truth-or-dare-db --remote` and
> `wrangler d1 execute truth-or-dare-db --remote --file=migrations/seed.sql`.

### Removing Tailwind CSS

If you prefer not to use Tailwind CSS:

1. Remove the demo pages in `src/routes/demo/`
2. Replace the Tailwind import in `src/styles.css` with your own styles
3. Remove `tailwindcss()` from the plugins array in `vite.config.ts`

## Deploy to Cloudflare Workers

This project uses the Cloudflare Vite plugin (configured in `vite.config.ts`) and `wrangler.jsonc`:

1. Install Wrangler: `bun add -g wrangler`
2. Authenticate: `wrangler login`
3. Deploy: `bun run deploy`

### Environment variables & secrets

Local secrets live in `.dev.vars` (copy from `.dev.vars.example`, then fill in
real values). Wrangler/Vite reads this file automatically for `bun run dev`.

- **Bindings** (`DB`, `ROOM_DO`) are declared in `wrangler.jsonc` and deploy
  automatically — no extra input needed.
- **Worker runtime secrets**: any key you add to `.dev.vars` (except the
  `CLOUDFLARE_*` tooling keys) is pushed to production automatically by
  `bun run deploy` via `scripts/sync-secrets.ts` (`wrangler secret put`,
  non-interactive) — no more typing secrets at deploy time.
- **Dev tooling**: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` and
  `CLOUDFLARE_D1_TOKEN` are read from `.dev.vars` by `drizzle.config.ts` for
  Drizzle Studio / remote D1 operations.

> **Security note**: `.dev.vars` is gitignored but is _not_ an encrypted
> secret store. It is meant for local development; if you use it to sync
> production secrets, keep it off shared machines and prefer CI secrets
> (e.g. GitHub Actions `secrets`) in team settings.

KV, D1, R2, and Durable Object bindings are configured in `wrangler.jsonc` — see https://developers.cloudflare.com/workers/wrangler/configuration/.

## Routing

This project uses [TanStack Router](https://tanstack.com/router) with file-based routing. Routes are managed as files in `src/routes`.

### Adding A Route

To add a new route to your application just add a new file in the `./src/routes` directory.

TanStack will automatically generate the content of the route file for you.

Now that you have two routes you can use a `Link` component to navigate between them.

### Adding Links

To use SPA (Single Page Application) navigation you will need to import the `Link` component from `@tanstack/solid-router`.

```tsx
import { Link } from '@tanstack/solid-router'
```

Then anywhere in your JSX you can use it like so:

```tsx
<Link to="/about">About</Link>
```

This will create a link that will navigate to the `/about` route.

More information on the `Link` component can be found in the [Link documentation](https://tanstack.com/router/v1/docs/framework/solid/api/router/linkComponent).

### Using A Layout

In the File Based Routing setup the layout is located in `src/routes/__root.tsx`. Anything you add to the root route will appear in all the routes.

More information on layouts can be found in the [Layouts documentation](https://tanstack.com/router/latest/docs/framework/solid/guide/routing-concepts#layouts).

## Data Fetching

There are multiple ways to fetch data in your application. You can use TanStack Query to fetch data from a server. But you can also use the `loader` functionality built into TanStack Router to load the data for a route before it's rendered.

For example:

```tsx
import { createFileRoute } from '@tanstack/solid-router'

export const Route = createFileRoute('/people')({
  loader: async () => {
    const response = await fetch('https://swapi.dev/api/people')
    return response.json()
  },
  component: PeopleComponent,
})

function PeopleComponent() {
  const data = Route.useLoaderData()
  return (
    <ul>
      <For each={data().results}>{(person) => <li>{person.name}</li>}</For>
    </ul>
  )
}
```

Loaders simplify your data fetching logic dramatically. Check out more information in the [Loader documentation](https://tanstack.com/router/latest/docs/framework/solid/guide/data-loading#loader-parameters).
